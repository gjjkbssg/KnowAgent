# Django-Agent 面试演示评估报告

## 评估设置

- 数据：4 份明确标注为合成数据的智能会议室资料，包含 Markdown 与 SVG 拓扑图。
- 问题：10 道，覆盖精确错误码、语义改写、规则阈值、跨文档关系、根因分析和多模态拓扑。
- 指标：Hit@5、Recall@5、MRR、平均检索延迟。
- 环境：本机 SQLite/FTS5/sqlite-vec/Neo4j，阿里云 Embedding 与 Rerank 接口。

## 最终实测结果

| 方案 | Hit@5 | Recall@5 | MRR | 平均延迟 |
|---|---:|---:|---:|---:|
| FTS only | 80% | 76.67% | 0.5083 | 0.83 ms |
| Vector only | 100% | 100% | 0.9000 | 256.89 ms |
| Hybrid raw | 100% | 96.67% | 0.8250 | 257.72 ms |
| Hybrid + Rerank | 100% | 100% | **0.9500** | 524.28 ms |
| Full pipeline | 100% | 100% | 0.5500 | 11,505.69 ms |

完整原始结果见 `results/retrieval_evaluation.json` 和 `results/retrieval_evaluation.csv`。

## 可以得出的结论

1. 向量召回解决了语义改写问题，在当前小样本集上召回完整。
2. Rerank 将 MRR 从向量召回的 0.90 提升到 0.95，说明它主要改善首条证据排序，而不是补充召回。
3. 原始分数相加的 Hybrid MRR 反而低于 Vector only，证明 FTS BM25 与向量距离不能直接跨尺度相加；应采用 RRF 或归一化融合。
4. Full pipeline 保持了召回，但平均延迟达到约 11.5 秒，且 MRR 降到 0.55。当前查询扩展、MMR、文档多样性和 GraphRAG 扩展更偏向增加证据覆盖，不适合作为排序指标的最优默认链路。
5. FTS 的价值是低延迟和精确标识符匹配，但中文默认 tokenizer 仍弱于专门的中文分词方案。

## 一次真实的缺陷闭环

初次评测时 FTS-only 全部为 0。排查发现有两个实现边界：

- FTS5 虚拟表返回的知识库 ID 是字符串，而评测调用方传入 UUID 对象，命中结果被错误过滤。
- FTS5 的 `tenant_id` 是未索引整数列，查询代码却传入字符串，虚拟表没有按普通 SQLite 表的方式完成类型归一。

修复 ID 归一和参数类型后，精确查询恢复；同时为 stock `unicode61` 对连续中文整句分词不足增加了有界的标识符/短语 LIKE 兜底。相关检索回归测试通过，FTS-only Hit@5 从 0 提升至 80%。

## 面试中如何表述

> 我没有把小样本上的 100% 包装成生产准确率。这个评测的意义是验证检索链各组件的相对贡献。结果说明向量负责召回，Rerank 负责首条排序；原始混合分数和完整流水线还有明确的融合、延迟优化空间。我也通过异常指标定位并修复了 FTS 类型边界问题。

## 后续改进

- 建立至少 100 道、包含负例与困难样本的人工标注集，并按主题隔离训练/调参和测试问题。
- 使用 RRF 或分通道 min-max/z-score 归一化替代原始分数相加。
- 使用支持中文分词的检索后端，或在入库和查询侧统一中文 tokenizer。
- 为查询扩展增加触发门限与缓存，GraphRAG 仅对关系型意图启用。
- 增加端到端答案忠实度、引用正确率、成本和 P95 延迟指标。
