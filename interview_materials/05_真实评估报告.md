# Django-Agent 面试演示评估报告

## 评估设置

- 数据：4 份明确标注为合成数据的智能会议室资料，包含 Markdown 与 SVG 拓扑图，入库后共 7 个 Chunk。
- 问题：10 道，覆盖精确错误码、语义改写、规则阈值、跨文档关系、根因分析和多模态拓扑。
- 指标：Hit@5、Recall@5、MRR、平均检索延迟。
- 模型：Embedding `text-embedding-v4`（接口返回 1024 维；该次运行按 `APP_EMBEDDING_DIM=384` 截取前 384 维存入 sqlite-vec）、Rerank `qwen3-rerank`、抽取与查询扩展 `qwen3.7-plus`、图片描述 `qwen3-vl-plus`。
- 存储：SQLite/FTS5/sqlite-vec，Neo4j 5。
- 复现：`python manage.py prepare_interview_demo --rebuild`，然后 `python manage.py run_interview_eval`。

## 实测结果

| 方案 | Hit@5 | Recall@5 | MRR | 平均延迟 |
|---|---:|---:|---:|---:|
| FTS only | 70% | 70% | 0.4833 | 0.36 ms |
| Vector only | 100% | 100% | 0.9000 | 930 ms |
| Hybrid raw（FTS + Vector，RRF） | 100% | 100% | 0.8000 | 931 ms |
| Hybrid + Rerank | 100% | 100% | **1.0000** | 2,217 ms |
| Full pipeline | 100% | 100% | **1.0000** | 3,897 ms |

完整原始结果见 `results/retrieval_evaluation.json` 和 `results/retrieval_evaluation.csv`。

## 可以得出的结论

1. 向量召回解决了语义改写问题。FTS 在 `semantic-cloud`、`aq-threshold`、`topology` 三道题上没有命中期望文档，向量通道全部命中。
2. Rerank 改善的是首条排序，不是召回：MRR 由 0.90（纯向量）、0.80（RRF 融合）提升到 1.00。
3. RRF 融合后的 MRR（0.80）低于纯向量（0.90）。RRF 只看名次，两个通道等权；FTS 通道较弱时，它排在前面的文档会把向量通道的第一名拉到第二。因此融合的作用是扩大候选集，最终排序由 Rerank 决定。
4. Full pipeline 与 Hybrid + Rerank 质量持平，平均多花约 1.7 秒（查询实体抽取、图谱查询）。在 7 个 Chunk 的语料上，GraphRAG、关系扩展和 MMR 没有带来可测量的排序收益。
5. FTS 的价值是亚毫秒延迟和精确标识符匹配，但中文默认 tokenizer 弱于专门的中文分词方案。

## 这组数字的限制

- 语料只有 7 个 Chunk，Top-5 几乎覆盖全部内容，Hit@5 和 Recall@5 的区分度很低；有参考意义的是 MRR。
- 10 道题、合成数据、出题人和实现者是同一个人，不代表生产准确率。
- 图片描述由视觉模型在入库时生成，每次重新入库文本略有不同，MRR 会有小幅波动（同一套代码两次入库，Hybrid + Rerank 分别为 0.95 和 1.00）。
- 该次运行的向量是 1024 维截断到 384 维，没有重新归一化，也没有和完整维度做过对比，所以 Vector only 的数字不代表该模型的完整效果。
- 延迟包含外部模型接口的网络耗时，单次查询在 2.5 到 5.9 秒之间（Full pipeline）。

## 与修复前的对比

旧数字测于检索排序修复之前。两次评测之间语料重新入库过，机器和网络也不同，不是严格的对照实验。

| 方案 | 修复前 MRR | 现在 MRR | 修复前延迟 | 现在延迟 |
|---|---:|---:|---:|---:|
| FTS only | 0.5083 | 0.4833 | 0.83 ms | 0.36 ms |
| Vector only | 0.9000 | 0.9000 | 257 ms | 930 ms |
| Hybrid raw | 0.8250 | 0.8000 | 258 ms | 931 ms |
| Hybrid + Rerank | 0.9500 | 1.0000 | 524 ms | 2,217 ms |
| Full pipeline | 0.5500 | 1.0000 | 11,506 ms | 3,897 ms |

- Full pipeline 的 MRR 由 0.55 到 1.00：旧实现把 GraphRAG 结果固定为 1.0 分，排在 Rerank 结果之前；现在 GraphRAG 只提供候选，和其他通道一起进入 RRF 和 Rerank。
- Full pipeline 的延迟：查询实体抽取原先开着模型思考、不限输出长度，单次 7 到 15 秒；关闭思考并限制为 300 token 后为 1 到 3 秒，抽查的 3 个问题里 2 个抽出的实体完全相同，1 个略有出入；评测指标没有变化。在同一份索引上，平均延迟由 12.1 秒降到 3.9 秒。
- Hybrid raw 没有因为换成 RRF 而变好，原因见结论 3。

## 用真实模型重跑时发现的三个缺陷

1. **图谱实体抽取的输出被截断，整批实体丢失。** 抽取请求的 `max_tokens` 是 1200，而两个较长 Chunk 的实体 JSON 约 3400 字符。截断后的 JSON 无法解析，代码把这一批当作没有实体，也不记日志。表现是《设备说明》这篇文档入库后图谱节点数为 0，第一轮评测中 Full pipeline 的 Hit@5 只有 90%。修复：上限提高到 4000，提示词要求紧凑 JSON；一批解析失败时退化为逐 Chunk 抽取；失败写 warning 日志。重新入库后该文档有 20 个节点。
2. **去重时短片段顶掉了包含它的完整片段。** SVG 的 OCR 结果只有几个设备型号，这些词全部出现在《设备说明》的正文里，被判为重复；旧逻辑保留分数高的一条，于是留下了只有几个词的 OCR 片段，正文被整段去掉。修复：两条内容篇幅相近时保留分数高的，一条被另一条包含时保留包含方。这个问题在缺陷 1 存在时才会在评测里显现（那时正文没有图谱通道的加分），缺陷 1 修复后，在同一份索引上新旧去重逻辑的评测结果相同，所以它由单元测试覆盖，而不是由评测数字证明。
3. **默认的 Rerank 地址是 404。** `.env.example` 把 Rerank 指向 `…/compatible-mode/v1`，而百炼的 Rerank 接口在 `…/compatible-api/v1/reranks`。Rerank 调用失败时静默返回原顺序，所以按默认配置部署时 Rerank 实际没有生效，也没有任何报错。修复：改正默认地址，并在代码里把 `compatible-mode/v1` 映射到 `compatible-api/v1`。

## 一次真实的缺陷闭环

初次评测时 FTS-only 全部为 0。排查发现有两个实现边界：

- FTS5 虚拟表返回的知识库 ID 是字符串，而评测调用方传入 UUID 对象，命中结果被错误过滤。
- FTS5 的 `tenant_id` 是未索引整数列，查询代码却传入字符串，虚拟表没有按普通 SQLite 表的方式完成类型归一。

修复 ID 归一和参数类型后，精确查询恢复；同时为 stock `unicode61` 对连续中文整句分词不足增加了有界的标识符/短语 LIKE 兜底。相关检索回归测试通过，FTS-only Hit@5 从 0 提升至 80%。

## 公开基准：DuRetrieval 子集

### 设置

- 数据：从 C-MTEB 的 DuRetrieval（`C-MTEB/DuRetrieval` 语料与问题、`C-MTEB/DuRetrieval-qrels` 的 dev 标注）按种子 `20261122` 抽 100 道问题，取它们的全部正例段落，再随机加负例段落。只用 600 字以内的段落，一个段落一个 Chunk，不建图谱和 Wiki。
- 两档规模：1,000 条负例（共 1,489 个 Chunk）和 5,000 条负例（共 5,489 个 Chunk）。负例是随机抽的，不是困难负例。
- 标注：按段落 ID，100 道题共 489 个正例段落，平均每题约 4.9 个。两档规模用的是同一批问题和正例，只是负例数量不同。
- 指标：MRR、Hit@k、Recall@k、nDCG@k（k = 1/3/5/10），按题平均；延迟另算 P50/P95。Recall 和 nDCG 按“找到多少个不同的正例”计算。
- 代码：抽样和入库在 `prepare_public_eval`，指标在 `personal_knowledge_base/eval_metrics.py`，评测入口仍是 `run_interview_eval`。

### 结果（5,489 个 Chunk）

| 方案 | MRR | Hit@1 | Recall@5 | Recall@10 | nDCG@10 | P50 延迟 | P95 延迟 |
|---|---:|---:|---:|---:|---:|---:|---:|
| FTS only | 0.3644 | 35% | 19.3% | 20.9% | 0.2385 | — | — |
| Vector only | 0.9770 | 97% | 85.5% | 94.9% | 0.9533 | 719 ms | 1,484 ms |
| Hybrid raw（RRF） | 0.9370 | 90% | 83.2% | 93.7% | 0.9113 | — | — |
| Hybrid + Rerank | 0.9711 | 96% | 85.2% | 96.1% | 0.9566 | 1,908 ms | 3,043 ms |
| Full pipeline | 0.9695 | 96% | 84.2% | 92.7% | 0.9371 | 2,290 ms | 3,725 ms |

### 结果（1,489 个 Chunk）

| 方案 | MRR | Hit@1 | Recall@5 | Recall@10 | nDCG@10 |
|---|---:|---:|---:|---:|---:|
| FTS only | 0.3838 | 37% | 20.2% | 25.5% | 0.2661 |
| Vector only | 0.9933 | 99% | 86.6% | 96.4% | 0.9763 |
| Hybrid raw（RRF） | 0.9603 | 94% | 83.6% | 94.9% | 0.9417 |
| Hybrid + Rerank | 0.9764 | 96% | 86.9% | 97.9% | 0.9753 |
| Full pipeline | 0.9671 | 95% | 84.9% | 94.3% | 0.9435 |

### 逐题对比（5,489 个 Chunk，按 nDCG@10）

| 对比 | 变好 | 变差 |
|---|---:|---:|
| Hybrid raw 对 Vector only | 1 | 19 |
| Hybrid + Rerank 对 Hybrid raw | 29 | 9 |
| Hybrid + Rerank 对 Vector only | 14 | 11 |
| Full pipeline 对 Hybrid + Rerank | 3 | 17 |

### 结论

1. **中文 FTS 是最大短板**：61 道题 FTS 的 Top-10 里没有任何正例。`unicode61` 分词器把连续中文切成一个词，`MATCH` 基本落空，回退到不排序的 `LIKE`。合成语料上 FTS 看起来还行（Hit@5 70%），是因为那里的问题大多带 `E42`、`XH-100` 这样的英文标识符。
2. **等权 RRF 在两个通道强弱悬殊时是负收益**：融合后比纯向量差的题有 19 道，好的只有 1 道。这和合成语料上 MRR 0.90 → 0.80 的现象一致，现在有了 100 道题的证据。改进方向是给通道加权，或在 FTS 换分词之后再评估。
3. **Rerank 的作用是修复融合的损失**：相对 RRF 29 好 9 差；相对纯向量只是小幅领先（14 好 11 差），两者差距在这个样本量下不能算显著。
4. **完整流水线的后处理在这个数据集上是负收益**：Recall@10 从 96.1% 掉到 92.7%。这里每个段落是独立的一条知识，所以“每篇最多两条”的限制不起作用；下降来自去重和 MMR：DuRetrieval 的多个正例常常是内容相近的段落，被当作冗余去掉了。MMR 适合“回答一个问题需要多样证据”的场景，不适合“把相关段落找全”的指标。
5. **规模从 1,489 扩到 5,489 个 Chunk，各方案下降 1 到 3 个百分点**，排序关系不变。

### 限制

- 问题都是单段落事实型，不覆盖多跳、跨文档、图谱和多模态，所以这组数字不能评价 GraphRAG。
- 负例是随机抽的，大部分和问题无关，检索比真实知识库容易；真实场景应加入困难负例。
- qrels 里有漏标：没被标为正例的段落里也可能有答案，这会让所有方案的分数偏低，但不影响方案之间的比较。
- 只取 600 字以内的段落，跳过了切分环节。
- 该次运行的向量仍是 1024 维截断到 384 维。
- 100 道题，两个方案相差一两道题不能当作差异。

## 领域困难集

### 设置

- 语料：`interview_materials/domain_eval_corpus/`，16 份合成文档，按 `chunk_size=420` 入库后 19 个 Chunk，建图谱和 Wiki（Neo4j 5）。
- 干扰设计：XH-100 与 XH-110 的 E42 含义不同；ES-20（120 秒、电池）与 ES-21（300 秒、常电）阈值不同；AP-50 与 AP-55 滤芯寿命不同；已废止的规则手册 v2.3 与现行 v2.4 只在数字上不同；3 份无关行政文档。
- 问题：`interview_materials/domain_eval_questions.json`，46 道，分 10 类（跨文档多跳 8、语义改写 8、相似型号干扰 6、精确术语 5、运维流程 5、版本冲突 4、数值条件 4、根因分析 3、设备能力 2、干扰文档 1）。
- 标注：`evidence` 为原文片段，结果 Chunk 去掉空白后包含该片段即命中；多跳题有 2 到 3 段证据，Recall 按找到几段计算。
- 噪声：同时检索 DuRetrieval 子集的 5,489 个段落（`--noise-kb-name`），共 5,508 个 Chunk。不加噪声的结果也记录了，各方案 MRR 高 0.01 到 0.04，排序关系不变。

### 结果（含噪声）

| 方案 | MRR | Hit@1 | Recall@3 | Recall@5 | nDCG@5 |
|---|---:|---:|---:|---:|---:|
| FTS only | 0.5543 | 45.7% | 60.5% | 65.9% | 0.5395 |
| Vector only | 0.8310 | 73.9% | 85.1% | 90.6% | 0.8008 |
| Hybrid raw（RRF） | 0.8100 | 69.6% | 87.3% | 96.7% | 0.8154 |
| Hybrid + Rerank | 0.8866 | 80.4% | 92.8% | 98.2% | 0.8770 |
| Full pipeline | 0.8884 | 80.4% | 94.9% | 98.2% | 0.8785 |

分类 MRR（Hybrid + Rerank）：精确术语 1.00、数值条件 1.00、根因分析 1.00、相似型号干扰 0.92、跨文档多跳 0.875、运维流程 0.85、语义改写 0.82、版本冲突 0.625。

### Hybrid + Rerank 首位没答对的 9 道题

| 题目 | 排第一的文档 | 问题 |
|---|---|---|
| version-aq3、version-lt2-idle | v2.3（已废止） | 旧版手册排在现行版前面 |
| version-v23-e17 | A301 复盘 | 复盘提到了 E17 和 AQ-3，压过了 v2.3 原文 |
| similar-xh110-e42 | 固件升级记录 | 记录里同时出现 XH-110 和 E42 |
| hop-c102-e17 | ES-20 规格 | 没先查到 C102 用的是 ES-21 |
| hop-b-wifi | 设备清单 | 清单排第一，手册排第二，属于证据顺序问题 |
| semantic-cloud、semantic-subdevice | DuRetrieval 噪声 / AP 说明 | 口语化问题被通用段落抢走 |
| ops-e43-level | XH-110 手册 | 问告警级别，排第一的是错误码定义 |

### 结论

1. **最需要改的是版本和有效性**：检索链完全不知道一份文档是否已废止。应在入库时记录 `status` / `effective_from` 等元数据，检索时过滤或降权，并在引用里显示版本。
2. **多跳题的第一跳靠的是语义相似，不是实体关系**：hop-c102-e17 需要先从设备清单得知 C102 装的是 ES-21，单次检索做不到；这是 Agent 多轮检索该解决的问题，而不是单次 GraphRAG 召回。
3. **GraphRAG 在这套题上仍没有可测量收益**（多跳类 MRR 与 Hybrid + Rerank 相同）。Full pipeline 只在 Recall@3 上高 2.2 个百分点，延迟多 1.6 秒。
4. **RRF 在有大量标识符的领域题上能扩召回**（Recall@5 90.6% → 96.7%），但会伤首位排序；在纯自然语言的 DuRetrieval 上则是净损失。两者合起来说明通道权重应按查询类型调整。

### 限制

- 46 道题，出题人和实现者是同一个人；每类 1 到 8 道题，只能看方向。
- 一篇文档只有 1 到 2 个 Chunk，切分边界造成的困难没有被覆盖。
- 只评检索，不评最终答案。

## 检索改进后的复测（中文二元组、加权 RRF、Rerank 阈值）

同一份数据、同一套模型，默认配置（向量 0.7 / 关键词 0.3 / 图谱 0.3，Rerank 阈值 0.4、兜底 0.15）。完整表格和结论见 README 的“检索改进”一节，这里只记录评测设置和需要在面试中说明的点。

- 额外跑了一次“二元组分词 + 等权 + 不设阈值”，用来把分词和权重的影响分开。
- 评测命令新增 `hybrid_rerank_threshold` 方案，并在每道题的明细里记录前 10 条的 Rerank 分数和是否为正例（`scores`、`gold_flags`），阈值是根据这两个字段的分布选的。
- qwen3-rerank 的分数分布：DuRetrieval 正例结果的 5% 分位是 0.54，非正例的中位数是 0.41；领域集正例的 5% 分位是 0.52，非正例的中位数是 0.38。两套数据前 10 条结果里没有一条低于 0.2，所以 WeKnora 默认的 0.2 在这里等于不过滤。
- 阈值是在评测集上选的，存在过拟合风险；它也只对 qwen3-rerank 有意义。
- 最终 Top-1 准确率没有变化。面试时应该说“全文检索通道修好了、融合排序更稳、送进上下文的无关片段减少”，不要说“检索准确率提升”。

沿用 PR #9 领域评测使用的同一数据库，只更新了 doc 06 的 lifecycle 元数据。以下为已定稿的真实模型结果，本次只补录，不重新计算。

|---|---:|---:|---:|---:|

| 领域集 MRR | 0.831 | 0.785 | 0.829 |
| 领域集 Recall@5 | 90.6% | 92.8% | 94.9% |
| 领域集 Hybrid raw（RRF）MRR | 0.865 | 0.844 | 0.868 |

Rerank 后三种设置的最终结果相同：DuRetrieval MRR 均为 0.972；领域集（不含版本策略）MRR 均为 0.887。384 维归一化后领域集分数下降没有按题分析，不能作因果判断。纯向量检索平均延迟约 1.1–1.3 秒，主要耗时来自 Embedding API。

已有的 384 维索引会继续按 384 维写入和查询（新向量截断后归一化），启动时提示 W001；运行 `python manage.py rebuild_vector_index` 后切换到 1024 维。

1024 维向量约 4 KB、384 维约 1.5 KB，存储量约为 2.7 倍。已有数据库需运行 `python manage.py rebuild_vector_index`，该命令会通过 API 为每个 Chunk 重新计算向量；我们为 5,514 个 Chunk 重建用时约 100 分钟。

## 面试中如何表述

> 我没有把小样本上的 100% 包装成生产准确率：语料只有 7 个 Chunk，Top-5 的召回率几乎没有区分度，我看的是 MRR。评测的意义是验证检索链各组件的相对贡献：向量负责召回，Rerank 负责首条排序，RRF 融合本身并不提升排序。完整流水线在这个规模上没有比 Hybrid + Rerank 更好，只是更慢，这一点我照实写在报告里。另外，用真实模型重跑时评测暴露了三个静默失败：抽取输出被截断、去重误删完整证据、Rerank 地址 404，这三个问题用模拟对象的单元测试都测不出来。
